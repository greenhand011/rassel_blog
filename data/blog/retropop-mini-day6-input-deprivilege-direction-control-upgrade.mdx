Day6 的核心变化其实可以压缩成一句话:

**我不再让按钮直接控制结果，而是只允许它们控制意图。**

这一步看起来像是一次小重构，实际上更像一次架构升级。因为它把输入从“直接改状态”降成了“只改方向”，然后再由系统统一在 `Tick` 里结算真正的移动。

## 为什么要做输入降权

前一阶段的写法是这样的:

- 按 `LEFT`，`playerX--`
- 按 `RIGHT`，`playerX++`

这能动，但问题也很明显: **用户输入直接修改核心状态。**

<img
  src="/static/images/GameCC/input-direct-movement-issues-table.png"
  alt="直接移动模型的问题表，说明输入直接控制世界状态时会带来什么风险"
  width="700"
/>

这类模型最大的问题不是不方便，而是太强了。它让输入和结果绑得太紧，后面一旦要做蛇、做节拍、做碰撞、做统一更新，都会变得很难收。

## 正确模型是先改意图，再改结果

所以我把它改成了经典的两段式:

```cpp
int dirX = 1;
int dirY = 0;

// Tick 里统一结算
playerX += dirX;
playerY += dirY;
```

输入不再直接改坐标，而是改方向。真正的位置变化，统一交给 `Game Tick`。

<img
  src="/static/images/GameCC/input-control-vs-action-table.png"
  alt="输入控制与结果执行的对比表，展示从直接控制坐标到修改方向的升级"
  width="700"
/>

这张对比图很适合放在这里，因为它就是这次改造的本质:

- 输入 = 意图
- Tick = 执行
- 渲染 = 展示结果

三者拆开之后，系统会清楚很多。

## 四个方向统一收口到行为函数

Day6 还做了一件很关键的事: 把 `UP / DOWN / LEFT / RIGHT` 全部收口到统一的行为函数里。

```cpp
void handleLeft() {
  if (currentState == STATE_GAME) {
    dirX = -1;
    dirY = 0;
  }
}

void handleRight() {
  if (currentState == STATE_GAME) {
    dirX = 1;
    dirY = 0;
  }
}
```

`UP / DOWN` 也一样，只是在菜单态继续控制菜单，在游戏态则改成方向控制。

这样做的好处是很直接的:

- 扫描层只负责读输入
- 行为层只负责解释输入
- 状态层只负责决定输入是否合法

系统从“按键到处写逻辑”变成了“输入先经过统一入口，再决定怎么走”。

## 为什么还要防 180 度反向

如果只是把方向键改成方向控制，贪吃蛇还是会有一个经典问题: 180 度反向。

比如当前向右，如果再按左，就会瞬间反向。对于蛇类游戏，这通常是不允许的，因为它会破坏规则，也会破坏玩家预期。

所以我给四个方向都加了合法性判断:

```cpp
void handleLeft() {
  if (currentState == STATE_GAME) {
    if (dirX != 1) {
      dirX = -1;
      dirY = 0;
    }
  }
}
```

其他方向同理。

这一步的意义很像状态机里的非法状态拦截:

- 不是所有输入都接受
- 输入先到系统
- 系统判断是否合法
- 合法才更新
- 非法就丢弃

这已经不是“会不会写按键判断”的问题了，而是在做规则约束。

## `Tick` 和输入开始分工

Day6 里我最满意的地方，是 `Tick` 和输入终于彻底分开了。

输入负责决定方向，`Tick` 负责推进状态，渲染负责画出来。这样一来，后面就可以自然地继续接:

- 碰撞检测
- 蛇身增长
- 食物刷新
- 游戏失败条件

也就是说，Day6 的结果不是一个临时效果，而是真正把贪吃蛇骨架往前推了一步。

## 安全意义

如果从安全视角看，Day6 做的是非常典型的“输入降权”:

- 过去: 按键直接改坐标
- 现在: 按键只改方向
- 更高一层: 系统统一结算位移

这就是最小权限原则在嵌入式里的一个特别具体的体现。

输入越弱，系统越稳。

输入越接近“意图”，而不是“结果”，后面的规则控制就越容易做，也越不容易乱。

## 今天的结论

Day6 不只是把蛇往前推了一步，更重要的是把整个系统的输入哲学改了:

- 不再让输入直接碰核心结果
- 不再让按键越权控制世界状态
- 不再把“能执行”当成“应该执行”

这一步之后，RetroPop Mini 的游戏骨架终于像样了。

如果要继续往下写，我下一步会很自然地开始考虑:

- 蛇身数据结构
- 食物随机生成
- 碰撞判定
- 游戏结束和重开

这些内容不再是“能不能做”，而是“在什么规则下做”。

而这，正是一个系统真正长出来的标志。
