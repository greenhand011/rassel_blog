# 引言：谁动了我的内存？

在 Linux 系统中，每一个运行的程序（进程）都生活在一个完美的幻觉里。它们认为自己拥有一座整齐划一的“摩天大楼”。然而，当一个函数（主函数）要给另一个函数（子函数）传递数据时，不同架构的 CPU 就像来自不同国家的设计师，有着完全不同的“交接方案”。

理解这些方案，是进行 **IOT 安全审计、二进制漏洞挖掘和固件逆向**的入场券。

---

## 第一部分：进程的“摩天大楼”模型

想象一个进程就是一座大楼，从顶层到底层的分布遵循着严格的逻辑：

1.  **顶楼（栈 Stack）：** 它是“向下生长”的。每进入一个函数，就像在大楼里加了一层临时的“办公隔间”。函数结束，隔间拆除。
2.  **地下室（堆 Heap）：** 它是“向上生长”的。程序员通过 `malloc` 申请的内存就在这里，杂乱但灵活。
3.  **仓库（数据段 Data/BSS）：** 存放全局变量。有些是初始化的（Data），有些是空着的（BSS）。
4.  **基座（代码段 Text）：** 存放 CPU 运行的二进制指令。它是只读的，谁也别想改。

**我们要解决的核心痛点：** 当 `main` 函数要调用 `big_func(1,2,3,4,5,6)` 时，这 6 个数字到底是怎么从 `main` 传递到 `big_func` 的“办公隔间”里的？

---

## 第二部分：x86 (32位) —— 传统的“压栈派” (cdecl)

在老旧的 32 位 x86 架构中，CPU 寄存器非常吝啬（只有 8 个通用寄存器）。它的策略是：**“寄存器太贵了，全部参数走楼梯（栈）！”**

### 1. 实战编译

```bash
gcc -m32 -S calling.c -o calling_x86.s
```

### 2. 汇编解剖

<img
  src="/static/images/IOT/calling_x86.png"
  alt="x86架构下参数通过push指令依次入栈的内存示意图"
  width="700"
/>

```assembly
pushl   $6          # 1. 把 6 扔进栈（最右边的参数）
pushl   $5          # 2. 把 5 扔进栈
pushl   $4
pushl   $3
pushl   $2
pushl   $1          # 3. 最后把 1 扔进栈（最左边的参数）
call    big_func    # 4. 跳进函数
addl    $24, %esp   # 5. 关键：清理现场！(6个int * 4字节 = 24字节)
```

**小白必读点：**

- **右往左压：** 为什么要先压 6 再压 1？因为栈是“后进先出”。这样子函数在读取时，第一个出来的就是参数 1，符合人类逻辑。
- **栈平衡：** 调用者 `main` 必须在函数回来后，手动把栈指针 `%esp` 往回挪 24 字节。这就好比你在地上放了 6 个盘子传给别人，别人用完了，你得负责把盘子捡走，否则大楼迟早会被盘子堆满（栈溢出）。

## 第三部分：ARM (32位) —— 高效的“混血派” (ATPCS)

ARM 是为了高效而生的。它认为：“去内存（栈）里拿数据太慢了，我们要用手（寄存器）直接递！”

### 1. 核心策略：前四后栈

ARM 拥有众多的寄存器。它规定：

- **R0 - R3：** 这四只“手”专门用来接前 4 个参数（VIP 通道）。
- **Stack：** 如果参数多于 4 个，剩下的才去挤栈（普通通道）。

### 2. 汇编解剖

<img
  src="/static/images/IOT/calling_arm.png"
  alt="ARM架构下R0-R3传递参数与栈传递多余参数的对比图"
  width="700"
/>

```assembly
@ 第一步：安顿那些“挤不上寄存器”的倒霉蛋 (5和6)
sub     sp, sp, #8       @ 栈顶向下挪8字节，腾出两个位子
mov     r3, #6
str     r3, [sp, #4]     @ 把 6 塞进仓库深处
mov     r3, #5
str     r3, [sp]         @ 把 5 塞进仓库门口

@ 第二步：让 VIP 参数坐上寄存器跑车
mov     r3, #4           @ R3 = 参数 4
mov     r2, #3           @ R2 = 参数 3
mov     r1, #2           @ R1 = 参数 2
mov     r0, #1           @ R0 = 参数 1
bl      big_func         @ 冲刺！调用函数
```

**小白必读点：**

- **溢出 (Spilling)：** 当参数变成 10 个时，ARM 会把前 4 个放寄存器，后 6 个全放栈里。在逆向分析 IOT 固件时，看到 `str rX, [sp]` 就要警惕，这通常是在传参。

## 第四部分：MIPS (32位) —— 严谨的“影子空间”派 (O32 ABI)

MIPS 架构在 IOT 设备（路由器、摄像头）中极度常见。它的设计极其古板且严谨，引入了一个让无数新手崩溃的概念：**影子空间 (Shadow Space)**。

### 1. 汇编解析

```assembly
li      $2, 6
sw      $2, 20($sp)    # 参数 6 存入栈偏移 20
li      $2, 5
sw      $2, 16($sp)    # 参数 5 存入栈偏移 16

li      $7, 4          # $a3 = 4
li      $6, 3          # $a2 = 3
li      $5, 2          # $a1 = 2
li      $4, 1          # $a0 = 1
jal     big_func       # 调用函数
nop                    # 延迟槽：MIPS 的特殊设计，防止流水线空转
```

### 2. 深度硬核：为什么要留出 16 字节的“空位”？

你会发现，参数 5 是存放在 `16($sp)` 的位置，而不是 `0($sp)`。
**这空出来的 0, 4, 8, 12 字节去哪了？**

这就是 MIPS 的**影子空间**。即使参数 1-4 已经用了寄存器 `$a0-$a3`，调用者依然要在栈上给它们预留出“位置”。

- **用途：** 如果子函数 `big_func` 觉得自己寄存器不够用了，它可以随手把寄存器里的参数 1 存到这片预留的影子空间里。
- **对比：** ARM 不预留空位，如果你想存，得自己临时在栈上开辟空间。MIPS 则强制要求：**“只要你调用函数，就得在栈顶先挖个 16 字节的坑，不管你填不填！”**

## 第五部分：GDB 活体解剖实战

光说不练假把式。我们直接看内存里的真相。

### 1. 准备调试

```bash
gcc -g calling.c -o calling_dbg
gdb ./calling_dbg
```

### 2. 观察命令流

在 GDB 中，我们要重点观察函数跳转前的一刹那：

```gdb
(gdb) break main            # 在 main 停下
(gdb) run                   # 跑起来
(gdb) disassemble main      # 反汇编 main
```

**关键观察点：**

- 如果是 x86，你会看到一连串的 `push`。你可以通过 `x/10xw $esp` 看到这些数字像叠罗汉一样整齐排列。
- 如果是 ARM，执行 `info registers`，你会看到 `r0` 到 `r3` 刚好就是 `1, 2, 3, 4`。
- 如果是 MIPS，输入 `x/4xw $sp`，你会惊讶地发现栈顶前 16 字节可能是随机垃圾值，因为那是“影子空间”，而 `16($sp)` 处才是稳稳的数字 `5`。

---

## 总结：给安全研究者的建议

当你面对一个未知的固件二进制文件时：

1.  **看前 4 个寄存器：** 在 ARM/MIPS 中，它们几乎总是函数的前几个参数。
2.  **找栈偏移：** 看到 `[sp, #0x10]` 这种偏移，通常意味着这是第 5 个及以后的参数。
3.  **找栈平衡：** 如果是 x86，函数调用后的 `add esp, XXX` 能告诉你这个函数到底接了多少个参数。
