Day1 的 RetroPop Mini，本质上还只是一个“静态开机图显示工程”：上电、初始化屏幕、把一张图推上去，然后程序基本不再做事。

Day2 的意义，就在于把它从“会亮的屏”推进成“有骨架的系统”。开机先显示 splash，随后自动进入主菜单；菜单里有 `Start Game`、`Gallery`、`About` 三个入口；最开始先用串口模拟方向和确认，随后再把真实按键接进来。看起来像是在做 UI，实际上是在搭一台掌机后续所有功能都要依赖的软件框架。

## 今天到底做成了什么

如果只用一句话概括今天的进展，那就是：

> 我把一个静态显示 Demo，升级成了一个可以启动、切页、导航，并且已经接入真实 GPIO 按键的最小掌机原型。

这一步完成之后，程序的行为已经很像一台真正的掌机了：

- 开机先显示原来的全屏图作为启动页
- 1.2 秒后自动切入主菜单
- 菜单支持上下移动高亮
- `e` 负责确认，`b` 负责返回
- 上下两个真实按键已经可以直接驱动菜单移动

## 从静态图片到最小掌机框架

### 为什么这一步不是加页面，而是在搭骨架

笔记里有一句话我很认同: 掌机天然就是一个“页面切换系统”。

开机页、菜单页、游戏页、图库页、关于页，本质上都是不同状态。只要你接受这一点，后面的代码组织方式就会一下子清晰起来。Day2 里最关键的改动，就是先把整台设备抽象成一个状态机：

```cpp
enum AppState {
  STATE_SPLASH,
  STATE_MENU,
  STATE_GAME,
  STATE_GALLERY,
  STATE_ABOUT
};

AppState currentState = STATE_SPLASH;
AppState lastState = STATE_ABOUT;
```

这段代码不花哨，但它非常重要。它相当于先回答了一个问题:

**此刻，这台掌机到底“处在哪一页”。**

一旦状态明确，输入该怎么响应、屏幕该画什么、什么时候允许返回，全都有了着力点。否则后面的逻辑很容易退化成一团不断膨胀的 `if else`，功能一多就开始失控。

主菜单的出现，标志着这个项目第一次从“静态显示”变成了“可导航的应用”。

### splash 为什么要用 `millis()`，而不是 `delay()`

Day2 里另一个很好的习惯，是没有直接写一个 `delay(1200)` 把程序堵死，而是用了非阻塞的时间控制：

```cpp
unsigned long splashStartTime = 0;
const unsigned long SPLASH_DURATION = 1200;

if (currentState == STATE_SPLASH) {
  if (millis() - splashStartTime >= SPLASH_DURATION) {
    currentState = STATE_MENU;
  }
}
```

这背后的意义并不只是“写法更高级”，而是你开始把程序当成一个持续运行的系统，而不是一串从上到下机械执行的脚本。

`delay()` 会让整个系统在那 1.2 秒里什么都做不了；`millis()` 则是在每一轮 `loop()` 里判断“时间是不是到了”。这正是后面做动画、游戏移动、定时器、菜单闪烁、输入扫描时必须建立起来的思维方式。

## 状态机如何把页面、输入和渲染拆开

### 只在状态变化时重绘，才是嵌入式屏幕该有的节奏

Day2 的代码里有一组很值钱的变量：`currentState` 和 `lastState`。

它们解决的不是“能不能画出来”，而是“要不要每一轮都重画整屏”。在桌面开发里，全屏刷新常常被视为理所当然；但在 ESP32-C3 驱动 ST7789 这种 SPI 屏幕的场景里，每一次整屏重绘都要付出真实成本：CPU 计算、SPI 传输、像素写入，后面再叠加按键、音效、游戏逻辑，浪费会越来越明显。

```cpp
void renderStateIfNeeded() {
  if (currentState == lastState) {
    return;
  }

  switch (currentState) {
    case STATE_SPLASH:  drawSplash(); break;
    case STATE_MENU:    drawMenu(); break;
    case STATE_GAME:    drawGamePage(); break;
    case STATE_GALLERY: drawGalleryPage(); break;
    case STATE_ABOUT:   drawAboutPage(); break;
  }

  lastState = currentState;
}
```

这种“状态变了再重绘”的习惯，短期看是在省性能，长期看是在给整个系统建立秩序。

### 菜单模型非常朴素，但已经足够稳定

Day2 的菜单实现其实很简单：一个菜单数组，一个当前选中索引，再加上上下移动时的循环边界处理。

```cpp
const char* menuItems[] = {
  "Start Game",
  "Gallery",
  "About"
};

const int MENU_COUNT = sizeof(menuItems) / sizeof(menuItems[0]);
int selectedIndex = 0;
```

向上时如果索引小于 0，就跳到最后一项；向下时如果超出范围，就回到第 0 项。这个逻辑今天用在三项菜单上，明天一样可以迁移到设置页、背包列表、图库分页，底层思路并不会变。

### 串口输入不是权宜之计，而是输入系统的脚手架

Day2 一开始没有真实按键，于是先用串口模拟输入：

- `w` 上移
- `s` 下移
- `e` 确认
- `b` 返回

这听起来像“临时方案”，但它其实非常聪明。因为在硬件还没有完全接稳之前，先把输入协议、菜单跳转、返回逻辑全部跑通，可以把“软件逻辑问题”和“硬件接线问题”拆开排查。

```cpp
char readInputCommand() {
  if (Serial.available() > 0) {
    char c = Serial.read();
    if (c >= 'A' && c <= 'Z') {
      c = c - 'A' + 'a';
    }
    return c;
  }
  return '\0';
}
```

从开发视角看，串口是调试窗口；从系统视角看，它也是一个清晰、可重复的输入源。先把系统跑顺，再把真实按键接进来，这种节奏是对的。

## 真实按键接入：难点从“有没有按下”变成“怎么才算按了一次”

### 先把四脚轻触开关看明白

文档里对按钮结构的描述非常关键。四脚轻触开关并不是“四个独立引脚”，而是天然分成两组：

- 没按下时，同一侧的两个脚彼此导通
- 没按下时，左右两侧彼此不导通
- 按下后，左右两组才会接通

这意味着接线时不能随便挑两个脚就焊，必须从左边取一个脚、右边再取一个脚，才能把“按下”这个动作真正变成电路状态变化。

按键正面看上去只是一个很普通的小元件，但如果没有先理解内部导通关系，后面写再多扫描代码也没用。

### 用万用表把“我觉得”变成“我确认”

真正有工程感的地方，在于没有停留在“看起来像这样”，而是用万用表去验证导通关系。

文档里的验证思路很扎实：

- 测同侧两个脚，不按下时也应该导通
- 测跨侧两个脚，不按下时不导通，按下后才导通

### 为什么消抖和边沿触发是输入系统的基础课

把按钮接上之后，真正的问题才刚刚开始。物理按键在按下和释放的瞬间会抖动，如果代码只是简单判断“现在是不是 `LOW`”，一次按压很可能会被识别成多次触发；如果手一直按着不放，`loop()` 每转一轮都可能再触发一遍，菜单就会疯狂跳动。

所以 Day2 的代码没有停在“读 GPIO”，而是进一步做了两件事：

- **消抖**：过滤几毫秒内的抖动变化
- **边沿触发**：只响应“从未按下到刚按下”的那一瞬间

```cpp
const unsigned long DEBOUNCE_MS = 30;

if ((now - lastUpChangeTime) > DEBOUNCE_MS) {
  static bool upHandledPressed = false;

  if (upNow == LOW && !upHandledPressed) {
    if (currentState == STATE_MENU) {
      moveSelectionUp();
    }
    upHandledPressed = true;
  } else if (upNow == HIGH) {
    upHandledPressed = false;
  }
}
```

这里最值得记住的，不是某个变量名，而是背后的输入模型：

- `INPUT_PULLUP` 让未按下时保持高电平
- 按下后读到 `LOW`
- 只有“下降到按下态”的那个边沿才算一次有效操作

这就是为什么按键系统一旦写对，整个菜单会突然变得“像产品”；而一旦写错，再好看的界面也会显得毛躁、不稳、不可控。

## 从开发视角，再看一眼“安全”

这份 Day2 笔记虽然以功能开发为主，但里面已经隐约出现了很多很典型的安全思维入口。

### 状态机，本质上也是边界控制

设备现在处于 `STATE_MENU`，还是 `STATE_GAME`，决定了同样一个输入应该触发什么行为。把状态写清楚，不只是为了代码整洁，也是为了减少“在不该响应的时候被响应”的混乱。

换句话说，状态机不仅是 UI 骨架，也是约束系统行为边界的第一层结构。

### 串口日志是调试窗口，也可能是观察窗口

Day2 里大量使用了类似 `[PAGE] MENU`、`[INPUT] w`、`[BUTTON] DOWN` 的串口输出。对调试非常有帮助，但这也提醒我：日志从来不只是给开发者看的，它同时也是系统行为的暴露面。

开发阶段要大胆打印，发布阶段则要学会收口，这是嵌入式系统迟早要面对的一步。

### 文档里残留的“引脚漂移”痕迹，反而很有价值

从笔记中的代码片段可以看到，`PIN_BTN_UP` 的说明里出现过 `3`，而串口说明又写过 `GPIO5 -> GND`。这类前后不一致，几乎就是硬件调试阶段最真实的痕迹。

它提醒我们的不是“某个数字写错了”这么简单，而是：

- 引脚定义要尽量集中管理
- 串口提示、注释、接线图、实际代码最好共用同一份事实来源
- 一旦系统进入多人协作或后续复盘阶段，模糊的引脚信息会迅速变成排障成本

很多嵌入式问题，并不是死在高难度算法上，而是死在这种看似很小的配置漂移上。

## 今天的收获，不是“又多了两个按钮”

Day2 真正完成的，并不是某两个 GPIO 的接线任务，而是把整个项目推进到了一个新的阶段：

- 系统第一次有了清晰的页面状态
- 输入、渲染、状态切换第一次被拆开
- 真实按键第一次接入软件逻辑
- 输入系统第一次开始认真处理抖动和边沿

从这里往后，RetroPop Mini 才真正有资格继续长出更复杂的东西，比如游戏逻辑、更多页面、音效、持久化配置，甚至再往前一步，去思考固件结构、调试接口暴露、输入边界和系统可信性。

对我来说，Day2 最硬核的地方不在于“功能比昨天多”，而在于很多以前模糊的概念，开始慢慢连成一条线了：

- 掌机不是几张界面图，而是一组明确的系统状态
- 按键不是焊上就能用，而是一整套电气结构与输入语义
- 能跑起来的程序，不等于结构已经稳了

这正是我想继续把这个项目写下去的原因。每往前推一天，做出来的不只是一个更像样的复古掌机，也是一个更容易被解释、更容易被分析、也更值得被认真理解的嵌入式系统。
