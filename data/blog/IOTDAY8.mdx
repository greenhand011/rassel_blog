# 引言：内存的虚实博弈

在 Linux 系统中，每一个运行的程序（进程）都生活在一个完美的幻觉里。它们认为自己拥有一座整齐划一的“摩天大楼”，拥有无限的空间。然而，当一个函数（主函数）要给另一个函数（子函数）传递数据时，不同架构的 CPU 就像来自不同国家的设计师，有着完全不同的“交接方案”。

理解这些方案（即**调用约定 Calling Conventions**），是我们进行二进制漏洞挖掘、ROP 链构造以及 IOT 固件逆向分析的绝对基本功。

---

## 第一部分：进程的“摩天大楼”模型

想象一个进程就是一座大楼，从顶层到底层的分布遵循着严格的逻辑：

1.  **顶楼（栈 Stack）：** **向下生长（高地址向低地址）**。每进入一个函数，就像在顶楼往下加盖了一层临时的“办公隔间”。函数运行结束，这个隔间直接作废拆除。传参、局部变量都在这里。
2.  **地下室（堆 Heap）：** **向上生长（低地址向高地址）**。程序员通过 `malloc` 或 `new` 手动申请的内存就在这里，杂乱但空间大、极其灵活。
3.  **仓库（数据段 Data/BSS）：** 存放全局变量和静态变量。其中 Data 段放已经赋了初值的，BSS 段放没有赋初值（默认清零）的。
4.  **基座（代码段 Text）：** 存放 CPU 运行的二进制机器指令。它是**只读**的，确保程序不会自我篡改代码。

## 第二部分：传参博弈 —— 谁坐包厢，谁挤硬座？

我们要解决的核心问题：当 `main` 调用 `func(1, 2, 3, 4, 5, 6)` 时，这 6 个数字怎么传？

### 1. x86 (32位) —— 传统的“压栈派”

x86 架构历史悠久，寄存器极度稀缺。它的策略很简单粗暴：“寄存器太贵了，全部参数走楼梯，塞进栈（Stack）里！”

```assembly
pushl   $6          # 把参数 6 压入栈
pushl   $5
pushl   $4
pushl   $3
pushl   $2
pushl   $1          # 最后把参数 1 压入栈（此时它在栈顶）
call    func        # 跳转执行子函数
addl    $24, %esp   # 栈平衡：main 负责清理这 24 字节的空间
```

- **小白必看：为什么从右往左压？** 因为栈是“后进先出”的数据结构。先压 6，最后压 1。这样子函数 `func` 伸手去栈顶拿数据时，第一个拿到的恰好是参数 1，完美符合人类阅读习惯。
- **清理规矩 (Caller-Cleanup)：** `main` 函数把别人搞乱的栈，在别人执行完后，必须自己打扫干净（把栈指针 `%esp` 拉回来）。

### 2. ARM (32位) —— 高效的“混血派”

ARM 追求极致的访存效率，访问内存（栈）太慢了。ARM 规定：**前 4 个参数坐 VIP 包厢（R0-R3），剩下的实在坐不下了，再去挤栈（普通硬座）**。

```assembly
@ 第一步：处理溢出的倒霉蛋参数 5, 6
sub     sp, sp, #8       @ 栈顶向下挖 8 字节的坑
mov     r3, #6           @ 临时借用 R3 搬砖
str     r3, [sp, #4]     @ 把参数 6 塞进栈深处
mov     r3, #5
str     r3, [sp]         @ 把参数 5 塞进栈顶门口

@ 第二步：让 VIP 参数坐上跑车
mov     r3, #4           @ r3 = 参数 4
mov     r2, #3           @ r2 = 参数 3
mov     r1, #2           @ r1 = 参数 2
mov     r0, #1           @ r0 = 参数 1
bl      func             @ 冲刺，跳转调用
```

### 3. MIPS (32位) —— 严谨的“影子空间”派

MIPS 和 ARM 一样，也是前 4 个参数走寄存器。但 MIPS 的设计师是个有强迫症的严谨狂，他强制要求：**无论参数在不在寄存器里，栈顶都必须为前 4 个参数预留好 16 字节的坑位（Shadow Space）！**

```assembly
li      $2, 6
sw      $2, 20($sp)    # 参数 6 存入栈偏移 20 的位置
li      $2, 5
sw      $2, 16($sp)    # 参数 5 存入栈偏移 16 的位置
                       # ⚠️ 为什么不存 0($sp)？因为 0-15 字节是死规矩，留给 $a0-$a3 的影子空间！
li      $7, 4          # $a3 = 参数 4
li      $6, 3          # $a2 = 参数 3
li      $5, 2          # $a1 = 参数 2
li      $4, 1          # $a0 = 参数 1
jal     func           # 跳转并链接 (Jump and Link)
nop                    # 延迟槽，防止流水线冲突
```

## 第三部分：MIPS 寄存器的“车间收纳管理条例”

MIPS 共有 32 个通用寄存器。想象一下，CPU 就是一个**“加工车间”**，这 32 个寄存器就是工位上的 32 个收纳盒。为了防止大家乱放东西导致系统崩溃，MIPS 制定了以下严格的条例。

### 1. `$zero` (0号)：永远的“垃圾桶”和“无底洞”

- **特性：** 不管你往里面写什么数字，它里面永远是 0。
- **用途：** 编程中 0 最常用。例如要把 `$t1` 的值赋给 `$t0`，可以直接 `add $t0, $t1, $zero`。不需要结果的废弃指令，也可以直接定向给它。

### 2. `$v0 - $v1` (2-3号)：老板的“收件箱”

- **角色：** 函数的 **返回值 (Value)**。
- **场景：** `main` (老板) 让 `func` (员工) 算加法。员工算完后，必须把结果放在 `$v0` 里。老板随后去 `$v0` 里拿。如果数据太大（比如 64 位），就带上 `$v1` 一起装。

### 3. `$a0 - $a3` (4-7号)：员工的“发件箱”

- **角色：** **参数传递 (Argument)**。
- **场景：** 老板必须先把原料（参数 1-4）装进这四个盒子里，员工上班第一件事就是去这里拿原料。

### 4. `$t0 - $t9` (8-15等)：公用草稿纸 (Caller-Saved)

- **角色：** **临时工 (Temporary)**。谁都能用，谁都能擦。
- **核心规则：** 你（主调函数）如果在 `$t0` 上写了重要数据，然后你去调用了别的函数。等你回来，`$t0` 可能已经被别人擦掉写了别的东西！**你不能生气**。如果你想保留，你必须在调用前自己把它抄到栈里。这叫**调用者保存 (Caller-Saved)**。

### 5. `$s0 - $s7` (16-23号)：私人保险柜 (Callee-Saved)

- **角色：** **长效存储 (Saved)**。
- **核心规则：** 这是极其安全的寄存器。你去调用别的函数，回来后里面的数据**绝对不会变**。
- **代价：** 如果子函数（被调函数）非要用你的 `$s0` 保险柜，它必须先悄悄把里面的东西备份到栈上，用完后，再原封不动地放回去。这叫**被调用者保存 (Callee-Saved)**。

### 6. `$sp` (29号) 与 `$ra` (31号)：生命线

- **`$sp` (Stack Pointer)：** 永远指向栈顶那个“夹子”。存数据就减小 `$sp`，取数据就增大 `$sp`。函数结束时，必须保证 `$sp` 还原到初始状态（栈平衡）。
- **`$ra` (Return Address)：** 回家的路标。执行 `jal` 指令时，CPU 会把下一行代码的地址偷偷写进 `$ra`。当函数执行 `jr $ra` 时，就能精准跳回调用处。

## 第四部分：深度总结对照表（建议截图保存）

| 寄存器组      | 编号  | 中文别名 | 谁负责保护？(关键)    | 用途描述                                         |
| :------------ | :---- | :------- | :-------------------- | :----------------------------------------------- |
| **`$zero`**   | 0     | 零       | N/A                   | 永远是 0，只读，清零专用。                       |
| **`$v0-$v1`** | 2-3   | 返回值   | 谁都不管              | 员工交给老板的工作成果。                         |
| **`$a0-$a3`** | 4-7   | 参数     | 谁都不管              | 老板交给员工的加工原料。                         |
| **`$t0-$t9`** | 8...  | 临时工   | **调用者 (Caller)**   | 草稿纸。函数调用后，数据大概率被毁，需自己备份。 |
| **`$s0-$s7`** | 16-23 | 保险柜   | **被调用者 (Callee)** | 私人资产。子函数敢动，就必须负责备份和复原。     |
| **`$sp`**     | 29    | 栈指针   | 硬件/OS               | 记录当前大楼（栈）盖到了哪一层。                 |
| **`$ra`**     | 31    | 返回地址 | 自己存栈保护          | 记录“我从哪里来，该往哪里回”。                   |

## 第五部分：GDB 活体解剖实战

概念看完了，我们直接上 GDB 看内存里的真相：

```bash
# 编译带调试信息的程序
gcc -g calling.c -o calling_debug
gdb ./calling_debug
```

在 GDB 内部，我们要重点观察函数跳转前的一刹那：

```gdb
(gdb) break big_func        # 在函数入口打断点
(gdb) run                   # 把程序跑起来
(gdb) info registers        # 查看此时的寄存器状态
```

- 如果是 **ARM**，你会看到 `R0` 到 `R3` 刚好就是 `1, 2, 3, 4`。
- 如果是 **MIPS**，敲击 `x/4xw $sp` 查看栈顶，你会惊讶地发现前 16 字节全是垃圾值（那就是强制留空的影子空间），而在 `16($sp)` 处才是真正的数字 `5`。

理解了这些，当你分析 IOT 设备的汇编代码时，一眼就能看穿数据的流转逻辑。
