Day 4 我已经把 sensor 模块的失败计数、连续故障和故障分级接进去了。到这一步，模块内部其实已经能自己判断“我现在健康还是不健康”，但它还只是一个只会自己看、自己说的系统。

Day 5 我这里不想急着往后堆更多调度或者更复杂的协议，而是先做一件更关键的事：给它补上第一个对外诊断接口。外部可以发命令，ECU 解析命令，然后把最近一次系统状态回给外部。

这一步看起来不大，但它的意义很实在。系统第一次有了“接口”，也就第一次有了真正的攻击面。后面不管是只读查询、写参数、解锁，还是更像车载诊断的协议结构，都是从这里往外长出来的。

## 今天要做的事

如果把 Day 5 压成一句话，那就是：

> 我不再只让 sensor 模块给我看日志，而是让它开始能被外部问、被外部查，并且回答的是系统已经整理好的状态。

这一天我主要补了四层东西：

- 输入侧：串口命令接收与缓冲
- 内部状态侧：保存最近一次报告 `g_lastReport`
- 输出侧：把当前状态格式化成诊断响应
- 对外交互侧：支持 `help / ping / status`

这就让系统从“内部读传感器、内部判断、内部打印”往前走了一步，开始像一个最小 ECU 了。

## 为什么先做这个

我这里没有先去做更复杂的任务拆分，也没有一上来就把诊断协议做得很重，原因很简单：现在最需要先确认的，不是“能不能支持很多命令”，而是“系统有没有一个干净的对外边界”。

如果没有这个边界，后面很容易变成这样：

- 诊断查询直接下到硬件里重新读传感器
- 状态输出和采集逻辑混在一起
- 只读命令、写命令、调试命令全部挤在同一个入口里
- 哪怕只是看一眼状态，也会把底层逻辑搅乱

这不是我想要的方向。对我来说，Day 5 先做的是一个最小但清晰的诊断入口，它不负责把系统变复杂，只负责把系统边界立起来。

## 现在系统已经到什么程度

到 Day 5 结束，系统已经不只是一个“传感器 demo”了。它至少具备了下面这些能力：

### 输入侧

- 能读取 MPU6050 的原始数据
- 能识别在线 / 离线 / 读失败 / 异常值

### 内部状态侧

- 能更新健康计数
- 能区分持续故障和瞬时故障
- 能做故障分级

### 输出侧

- 能输出结构化 `SensorReport`
- 能把当前状态整理成稳定的报告对象

### 对外交互侧

- 能通过串口接收命令
- 能识别 `help / ping / status`
- 能把最近一次状态通过诊断口返回出去

这一步很重要，因为它说明系统开始真正有“输入、内部状态、输出、外部访问”这四层了。

## 主链路怎么跑

这一天我最想保住的，其实就是主链路的清晰度。现在代码的调用顺序大致是这样：

```cpp
loop()
  -> sensorReadFrame()
  -> buildSensorReport()
  -> printReport()
  -> diagPoll()
```

我这里把它拆开看，会更容易理解：

### `sensorReadFrame()`

这一步负责从底层硬件读一帧数据，判断传感器在线不在线，读出来的值正不正常，然后顺手更新健康计数。

它做的事很基础，但很关键，因为后面的所有状态判断都建立在这里。

### `buildSensorReport()`

这一步把原始 frame 和 health 计数聚合成结构化报告。

我更愿意把它看成“把散的状态整理成 ECU 能用的状态对象”，而不是单纯拼一个打印字符串。

### `printReport()`

这一步还是偏调试用途，负责把当前状态周期性打印出来，方便我看系统有没有跑偏。

### `diagPoll()`

这一步就是 Day 5 新加的对外入口。

它不直接碰传感器硬件，而是负责盯着串口，看看外部有没有发命令进来。

## `g_lastReport` 是干什么的

```cpp
SensorReport g_lastReport = {};
```

这个对象是今天最核心的一个点。

它保存的是“最近一次系统状态报告”。我可以把它理解成 ECU 手里随时拿着的一份最新体检结果。

这样做的好处很直接：外部问 `status` 的时候，不需要临时再去读一次硬件，而是直接把这份最近一次已经整理好的报告返回出去。

这样一来，诊断查询和传感器采集就分开了：

- 采集层负责更新状态
- 诊断层负责读取状态

这比“诊断接口一来就自己去读硬件”要干净得多。

如果没有 `g_lastReport`，系统很容易退回成一种很别扭的结构：每次外部查询都要临时重新采一次，查询逻辑和采集逻辑搅在一起，后面再想往上加任务分层会很难受。

## `g_cmdBuffer` 为什么必须有

```cpp
String g_cmdBuffer = "";
```

这个缓冲区是给串口命令准备的。

串口不是把一整条命令一次性塞进来的，通常是一个字符一个字符地到达。比如你输入 `status`，系统实际收到的是 `s`、`t`、`a`、`t`、`u`、`s` 这样的流。

所以这里必须先把字符攒起来，等遇到行尾，再统一交给命令处理函数。

这一步我没有写得太花，因为它本质上就是一个最小命令缓冲器，但它的意义不小：

- 它让输入变成流式处理
- 它让命令接收和命令执行分开
- 它也给后面扩展更复杂的诊断命令留了位置

我这里还给它加了长度限制，避免命令无限增长。现在这还不是完整的安全机制，但至少说明系统开始考虑输入边界了。

## `diagPoll()` 是怎么工作的

`diagPoll()` 其实就是串口命令接收器。

它只做两件事：

1. 从串口里读字符
2. 把完整命令交给处理函数

核心逻辑大致是这样：

```cpp
void diagPoll() {
  while (Serial.available() > 0) {
    char c = (char)Serial.read();

    if (c == '\r') {
      continue;
    }

    if (c == '\n') {
      if (g_cmdBuffer.length() > 0) {
        handleDiagCommand(g_cmdBuffer);
        g_cmdBuffer = "";
      }
    } else {
      g_cmdBuffer += c;

      if (g_cmdBuffer.length() > 64) {
        g_cmdBuffer = "";
        Serial.println("[DIAG] command too long");
      }
    }
  }
}
```

我这里按几个点拆开说：

- `Serial.available() > 0` 的意思是串口缓冲区里还有字符没处理
- `Serial.read()` 每次只读一个字符
- `\r` 直接忽略，因为我这里把 `\n` 当作命令结束
- 遇到 `\n`，说明一条命令完整了，就交给 `handleDiagCommand()`
- 普通字符就追加到 `g_cmdBuffer`
- 长度超过 64，就直接清空并给出提示

这里我最在意的不是代码多漂亮，而是它有没有把“输入收集”和“业务处理”分开。因为一旦后面要加参数命令、解锁命令、只读和写入分权，这个结构就能继续往上长。

## `handleDiagCommand()` 做了什么

```cpp
void handleDiagCommand(String cmd) {
  cmd.trim();
  cmd.toLowerCase();

  if (cmd == "help") {
    printDiagHelp();
    return;
  }

  if (cmd == "ping") {
    Serial.println("[DIAG] pong");
    return;
  }

  if (cmd == "status") {
    printDiagStatus();
    return;
  }

  Serial.print("[DIAG] unknown command: ");
  Serial.println(cmd);
  Serial.println("[DIAG] type 'help'");
}
```

这段代码的本质其实很简单：命令分发。

我这里先把输入做了两件小处理：

- `trim()` 去掉前后空白
- `toLowerCase()` 统一大小写

这样用户输入 `STATUS`、`Status`、`status`，系统都能当成同一个命令来处理。

然后命令分成三类：

- `help`：看支持什么命令
- `ping`：测试链路是否通
- `status`：返回当前状态

剩下的都算未知命令，系统会明确告诉你，不会装作自己懂了。

我特别保留 `status` 这个只读命令，是因为它最能体现今天这一步的价值：外部不是来“抢着读硬件”的，而是来读系统已经整理好的状态。

## `printDiagStatus()` 为什么不能重新读传感器

`printDiagStatus()` 的职责不是再读一次 MPU，而是把 `g_lastReport` 格式化输出给外部。

这点我这里故意分得很清楚，因为它代表两层东西：

- 采集层：负责让状态更新
- 诊断层：负责把当前状态说出去

如果诊断命令又跑去重新读硬件，那这个边界就塌了。外部查询不再只是查询，而是会反过来影响采集链路。

对我来说，这不是一个小细节，而是整个结构能不能继续往 ECU 方向走的关键。

## 我为什么把它看成攻击面

Day 5 最重要的一个认知变化，是我开始把这个诊断入口当成攻击面来看。

这不是危言耸听，而是很实际的工程判断：只要有外部输入，就一定要考虑输入边界；只要有能查询内部状态的接口，就一定要考虑它后面还能不能扩展成读写分权、鉴权和解锁。

现在我还没有做真正的 access control，也没有做复杂的挑战应答，但接口已经立起来了。后面要做安全设计，就不再是空谈。

## 这一天我真正想保住的节奏

我自己回头看，Day 5 做得最对的一件事，不是命令多了几个，而是节奏没有乱。

我没有因为已经能打印状态，就急着把所有事情都塞进 `loop()`；也没有因为想做诊断，就直接把协议做得很重。相反，我先把最小的输入出口搭出来，再让它只读、只查、只返回已有状态。

这个节奏对后面很重要，因为它决定了后面的 `sensor task`、`diag task`、以及更完整的通信层，不会从一开始就长歪。

## Day 5 之后，你至少要能回答的几个问题

这一天结束，我觉得下面这些问题应该能自己讲清楚：

- 为什么 `status` 不直接重新读一次传感器，而是读 `g_lastReport`
- 为什么串口命令要先缓冲，而不是一收到就处理
- 为什么 `diagPoll()` 要忽略 `\r`
- 为什么命令长度要限制在 64 字符以内
- 为什么 `handleDiagCommand()` 要先 `trim()` 再 `toLowerCase()`
- 为什么我把 `help / ping / status` 这三个命令放在最小诊断入口里
- 为什么说这个接口一旦存在，就已经是攻击面了
- 为什么只读命令和以后可能的写命令不能用同一种态度看待
- 为什么 `SensorReport` 比直接打印一堆变量更像 ECU 的输出方式

这些问题如果能讲顺，Day 5 就不是“多写了几个函数”，而是真的把系统边界往前推了一步。

## 结尾

Day 5 我没有继续把 sensor 模块做得更花，而是先给它加上了第一个能对外交互的诊断入口。这样做以后，系统第一次有了明确的输入边界，也第一次把“内部状态”变成了“外部可问、可查”的东西。

这一步还不是终点，但它很关键。因为后面不管是更完整的诊断协议、读写分权，还是更像车载系统的安全控制，前提都得是先有这个入口。
