这篇记录最有价值的地方，不是最后得出了 `A = TX、B = RX、C = GND、D = VCC` 这个结论，而是它把整条判断链都留下来了：先怎么测，第一次为什么没成功，为什么要换方法，换完以后看到了什么，最后又是怎么排错的。

对象还是那块带 `SJ1` 四孔预留位的 TP-LINK 路由器主板。目标很具体：把 `SJ1` 这四个孔里谁是 `GND`、谁更像 `VCC`、谁在启动时会主动往外发日志、以及为什么后来会出现乱码，全部一步一步理清楚。

## 先把孔位编号，不然后面根本没法讨论

在真正动万用表之前，原始记录做的第一件事不是连线，而是先把 `SJ1` 这四个孔顺着排下来编号。

<img
  src="/static/images/Router/router-uart-header-labeled.jpg"
  alt="SJ1 四个孔先按从上到下编号，后续所有测量和判断都以这个编号为基础"
  width="700"
/>

这一步看起来很小，但它是整篇实验记录能成立的前提。  
如果一开始不把孔位叫法统一，后面无论是记录导通结果、电压结果，还是讨论“哪一根线接到哪一个孔”，都会立刻陷入混乱。

## 第一件事：先找 GND

### 第一轮尝试：黑表笔放“大概率接地的大金属”，红表笔依次碰 1 到 4 号孔

原始笔记里找 `GND` 的第一轮尝试非常标准，而且这部分必须保留，因为很多人第一次摸 UART 都是这么开始的：

1. 万用表调到蜂鸣档 / 导通档
2. 黑表笔固定在“确定接地的大金属”上
3. 红表笔依次去碰 `1`、`2`、`3`、`4` 号孔

黑表笔优先放的候选点，也写得很清楚：

- 网口金属外壳
- `WAN / LAN` 口外面的金属壳
- 主板上其它大块裸露金属外壳
- `DC` 外圈金属

<img
  src="/static/images/Router/router-multimeter-continuity-mode.jpg"
  alt="万用表切到蜂鸣档，作为第一轮导通测试的起点"
  width="700"
/>

### 但第一轮的结果是：1 到 4 号孔全都不响

这正是原始记录最不能删掉的部分。  
因为它没有直接跳到“后来换方法就好了”，而是把第一次失败留下来了：

- 万用表本身没问题
- `SJ1` 这个区域也大概率没找错
- 但照着“黑表笔放 DC 外圈”这个常见经验去测时，`1 ~ 4` 号孔都没有得到蜂鸣反馈

也就是说，问题不是“完全找错地方”，而是**常见做法在这块板子上没有直接给出答案。**

### 为什么没响：常见做法不是宇宙铁律

原文紧接着解释了一个边界，这一点特别值得保留。

圆孔 `DC` 电源口一般会有两部分导电结构：

- 中间那根 / 中心接触点
- 外面这一圈金属套筒（outer sleeve）

常见约定里，中心是电源正极，外圈套筒是 `GND`。但原文特别提醒得对：**这只是常见做法，不是宇宙铁律。**

<img
  src="/static/images/Router/router-dc-jack-structure.jpg"
  alt="圆孔 DC 电源口的结构示意，用来说明外圈经常是地，但不能脱离实测直接下结论"
  width="700"
/>

这就是为什么第一轮没响，不能简单理解成“UART 找错了”。更合理的解释是：

- 你选的“参考地”位置，不一定正好和你当前测的路径形成了可直接导通的关系
- 或者你需要把观察点从外部金属壳，换到更接近焊点本身的位置

## 翻到背面：重新确认 DC 焊脚和 SJ1 孔位

第一轮没有结果之后，原始记录没有乱试，而是把板子翻到背面，重新给焊脚命名。

`DC` 电源座背面三个大焊脚，被命名为：

- `P1` = 左边
- `P2` = 下方
- `P3` = 右边

`SJ1` 背面四个小孔，从左到右被记成：

- `A`
- `B`
- `C`
- `D`

<img
  src="/static/images/Router/router-dc-jack-solder-pins.jpg"
  alt="主板背面 DC 电源座的三个大焊脚，用来重新定义 P1、P2、P3"
  width="700"
/>

<img
  src="/static/images/Router/router-uart-holes-back.jpg"
  alt="SJ1 背面四个小孔的对应位置，从左到右记为 A、B、C、D"
  width="700"
/>

然后原文给出了非常关键的导通矩阵，这里必须原样保留：

```text
P1: A不响 B不响 C不响 D不响
P2: A不响 B不响 C不响 D不响
P3: A不响 B不响 C响    D不响
```

这个结果的重要性在于，它终于不是“凭感觉说某个孔像地”，而是明确出现了一组稳定对应关系：

- 只有 `P3 -> C` 这一组出现导通
- 因此 `C = GND`

<img
  src="/static/images/Router/router-uart-ground-confirmation.jpg"
  alt="通过导通测试确认只有特定焊脚与 C 孔连通，从而把 C 判定为 GND"
  width="700"
/>

到这里为止，`GND` 才算真正站稳。

## 第二件事：找 VCC

`GND` 一旦确认，后面的测量才有了可靠参考点。原始记录接下来的顺序也非常标准：

1. 路由器先断电
2. 万用表从蜂鸣档切到直流电压档
3. 如果是手动档，先打到 `20V DC`
4. 黑表笔固定在刚确认出来的 `C`
5. 路由器上电
6. 红表笔依次去测 `A`、`B`、`D`

原文把实测结果也写得很明确，这里不能压缩成“测出一个 VCC”：

```text
A = 0V
B = 0V
D = 3.36V
```

为什么 `3.36V` 这一类结果更像 `VCC`？

- 因为 UART 相关接口常见逻辑电平就在 `3.3V` 左右
- `A` 和 `B` 在这一步静态测得都是 `0V`
- `D` 却稳定落在 `3.36V` 左右

所以到这一步，比较合理的判断就是：

- `C = GND`
- `D` 大概率是 `VCC`

这里也要保留一个很重要的边界：  
`VCC` 在这一步的价值，主要是帮助缩小孔位范围，不是为了把外部电源往板子里送。

## 第三件事：找 TX，但第一思路没成功

原文没有直接跳到“后来我用 USB-TTL 找到了 TX”，而是先保留了一个失败尝试，这一点非常重要。

当时的想法是：

- 万用表继续保持直流电压档
- 黑表笔固定在 `C`
- 红表笔先放在 `A`
- 路由器断电后重新上电
- 盯着开机前几秒，看 `A` 会不会出现明显跳变

要观察的，其实就是：

- 是不是从 `0V` 附近突然跳一下
- 是不是会快速变化
- 然后再回到某个值

同样的方法，又在 `B` 上重复了一遍。

但原始记录给出的结果很直接：

> 上述方法不管用，都是 0。

这一步不能删，因为它告诉读者两件事：

1. “看开机瞬间电平跳变找 TX”是一个合理思路，但不是每次都能靠万用表看出来
2. 当这条路不奏效时，下一步不是瞎试，而是换一种更适合观察串口输出的方法

## 改用 USB-TTL，但先做 RX-only 嗅探

这一步正是整篇 UART 文章里最值得保留的方法论之一。

原文明确写成了 `RX-only` 嗅探，也就是：

- 只连地
- 只连 USB-TTL 的 `RX`
- 不连 USB-TTL 的 `TX`
- 绝对不把 USB-TTL 的 `VCC` 接到板子的 `D`

<img
  src="/static/images/Router/router-usb-ttl-adapter.jpg"
  alt="用于串口嗅探的 USB-TTL 模块，当前阶段只用到 GND 和 RXD"
  width="700"
/>

为什么这样更安全？

- 现在的目标只是“听”板子有没有主动往外发日志
- 只要不把 `TX` 连过去，就不会先向板子主动送数据
- 不把 `VCC` 接回去，也能避免把外部供电线误送到板子上

也就是说，这一步不是为了“能不能交互”，而是为了先用最低风险确认：**哪一个孔在启动时会主动发串口日志。**

## 第一轮接法与 PuTTY 设置

原文这部分不能再被写成一句“打开串口工具”。它其实保留了非常完整的一轮设置过程：

第一轮接法是：

- 你的 USB-TTL `GND` -> 路由器 `C`
- 你的 USB-TTL `RXD` -> 路由器 `A`
- 其它都不接

接下来在电脑侧做的事情也很具体：

1. USB 转 TTL 先插到电脑上
2. 先确认电脑识别出来的是哪一个 `COM` 口
3. 这时候路由器先不要上电
4. 打开串口软件，这里用的是 `PuTTY`

`PuTTY` 的关键设置，原文给得很清楚：

```text
Speed (baud): 115200
Data bits:    8
Stop bits:    1
Parity:       None
Flow control: None
```

<img
  src="/static/images/Router/router-putty-session-settings.jpg"

  width="700"

<img

  width="700"
/>

为什么这里特别要写出“无流控”？

- 因为这类简单 TTL 串口连接，通常不会把硬件流控线也一起接出来
- 如果软件端误开流控，串口工具可能会等待并不存在的握手信号
- 结果就是明明线没接错，却什么都看不到

点 `Open` 之后，会弹出一个黑色窗口。原文也特别提醒：

- 这时窗口黑着是正常的
- 因为路由器还没上电，还没有开始“说话”

## 成功抓到启动日志后，哪些孔位就站住了

当路由器上电后，原始记录成功抓到了启动日志。这一步一旦成立，前面那条识别链就开始闭环了。

首先能确认的孔位关系是：

- `A = 路由器 TX`
- `C = GND`
- `D = VCC`（约 `3.36V`）
- 剩下的 `B = 路由器 RX`

其次，启动日志里还出现了几条非常关键的板级信息：

- `U-Boot 1.1.4`
- `AP99 (ar7241 - Virian)`
- `DRAM: 32 MB`
- `Flash: 4 MB`

<img
  src="/static/images/Router/router-boot-log-summary.jpg"
  alt="启动日志摘要截图，其中可见 U-Boot 版本、平台名、DRAM 和 Flash 容量信息"
  width="700"
/>

这几行信息的价值非常大，因为它不仅说明串口链路通了，还把板子的启动阶段、平台信息和存储规模都暴露出来了。前一篇硬件识别里关于 `Flash 4 MB`、平台和主控候选的判断，到这里也获得了新的旁证。

## 三根线都接上后，怎么验证串口是不是可交互

原文在确认 `A / B / C / D` 的角色之后，继续做了交互验证。接线方式变成：

- 模块 `GND` -> `C`
- 模块 `RXD` -> `A`
- 模块 `TXD` -> `B`

然后再按下面这个顺序操作：

1. 保持 `PuTTY` 黑窗口开着
2. 路由器断电
3. 再次上电
4. 盯着启动日志往下刷
5. 先不要乱按键
6. 等日志基本停下来以后，只按一次 `Enter`

这里“只按一次”很重要。原文强调得对：

- 不要长按
- 不要狂按
- 先给设备一个正常启动的机会，再测试它是否接受输入

### 可能出现的三种结果

这部分是当前坏稿里被压得最厉害的一段，但其实它非常有用，因为它把观察结果分类了。

#### 情况 1：出现提示符

比如出现：

- `#`
- `ar7240>`
- `tpl`
- `login:`
- 或其他可输入提示

这说明串口已经不只是“能看”，而是已经具备一定交互能力。

#### 情况 2：按 Enter 后没有任何变化

这通常意味着：

- 系统没开交互控制台
- 时机不对
- 设备还停在别的阶段

原文这里的态度也值得保留：这不代表失败，只代表当前这一次输入没有被接住。

#### 情况 3：按 Enter 后出现奇怪字符

这说明更可能是：

- 发过去的数据没有被正确识别
- 接触不稳
- `TXD -> B` 这一侧的链路存在问题

原文还提到一个额外的观察点：如果启动日志里出现类似

- `Autobooting in 1 seconds`
- `Hit any key to stop autoboot`
- `Press any key`

这样的提示，它说明引导阶段本身暴露出了人工干预窗口。这个事实本身值得记下，因为它反映了 bootloader 的行为边界；但这篇文章的重点还是先放在“串口识别与交互验证”，不往后继续展开。

## 乱码排错：不是只有一种可能

原始记录在这里没有简单地说“后来又好了”，而是认真把排错链写下来了。这部分对读者特别有帮助。

### 1. 先查 USB-TTL 模块的 TXD 空闲电压

原文第一反应非常合理：先确认问题是不是出在 USB-TTL 模块本身的逻辑电平上。

因为很多这类模块板上会同时标：

- `3V3`
- `+5V`

但这不自动等于：

- `TXD / RXD` 一定是 `3.3V` 逻辑

有些模块的 `3V3` 只是电源引脚，真正的 `TXD` 逻辑电平未必跟着一起切到 `3.3V`。如果 `TXD` 实际打出来是 `5V`，而你又直接把它送到路由器这边的 `B`（`3.3V RX`）上，就可能出现：

- 乱码
- 输入异常
- 甚至有损伤风险

原文在这里的测量步骤也要保留：

1. 先把模块 `TXD -> 路由器 B` 这根线拔掉
2. 让 USB-TTL 模块只插在电脑上
3. 万用表切到 `DC 20V`
4. 黑表笔放模块 `GND`
5. 红表笔放模块 `TXD`

最后测得大约就是 `3.3V`，这说明模块逻辑电平大概率没有问题。

### 2. 再做 USB-TTL 自检回环测试

这一步的价值在于，它能把问题一刀切开。

如果回环正常，说明下面这条链是好的：

```text
电脑 -> 模块 TXD -> 模块 RXD -> 电脑
```

那问题就更可能出在路由器 `B` 这一侧，或者接触状态本身。

原始记录里的回环步骤也非常清楚：

1. 模块和路由器全部断开
2. 只让模块插在电脑上
3. 把模块自己的 `TXD` 和 `RXD` 短接
4. 在 `PuTTY` 里输入几个字符，再按一次回车

预期结果是：

- 输入什么
- 窗口里就原样返回什么

比如输入 `abc123`，最后看到的也应该是 `abc123`。

原文记录的结果是：回环正常。  
于是问题范围继续缩小：更可能是路由器 `B` 侧接触不稳。

### 3. 最终确认更像是 B 侧接触问题

原文里有一句非常“实验现场”的描述：我这里采取的方法是用手握紧。

这句不该删，因为它正好说明问题并不神秘，而是很可能落在机械接触层面。整理成博客后，更专业一点的表述可以是：

> 最终判断主要问题在于 `B` 侧接触不稳，临时通过手动压紧接触改善了链路状态。

这也是板级实验里很真实的一部分：

- 理论没错
- 参数没错
- 模块自检也没错
- 结果最后卡在一根线、一只探针，或者一个接触不稳的孔位上

## 当出现登录提示后，该怎么理解当前状态

原文最后还记录了一个很实际的结果：

- 串口已经出现登录提示
- 试过 `admin`、`root`、`sohoadmin` 等输入
- 但并没有直接通过

这部分信息也不该删，因为它说明了一件事：  
**“串口链路建立成功”** 和 **“系统层面的认证被绕过”** 是两件完全不同的事情。

对这篇文章来说，更适合保留的结论是：

- 现在已经确认串口可观察
- 在接触状态改善后，也可以进入登录提示阶段
- 但认证行为本身仍然受设备当前固件状态约束

也就是说，到这里最值得带走的不是“怎样继续往里走”，而是：这条 UART 链路已经被确认通了，而且排错过程也说明问题并不在串口参数，而更像在接触质量上。

## 这篇文章真正教会了什么

把整条实验线索回看一遍，最有价值的其实不是某一个孔位的最终答案，而是这一整套顺序：

1. 先给孔位编号
2. 先找 `GND`
3. 再测 `VCC`
4. `TX` 的第一思路如果失败，不要硬猜，换成更稳的观察方式
5. 先做 `RX-only` 嗅探，再确认谁在主动发日志
6. 三线接齐后再做交互验证
7. 一旦出现乱码，先分清是电平问题、模块问题，还是接触问题

这就是为什么原文里那些失败尝试、矩阵记录、数值结果和排错过程都必须保留下来。因为真正能帮到读者的，从来不是一句“最后我找到了 UART”，而是这整条“为什么 -> 怎么判断 -> 观察到了什么 -> 结论是什么 -> 下一步该排什么”的链路。
