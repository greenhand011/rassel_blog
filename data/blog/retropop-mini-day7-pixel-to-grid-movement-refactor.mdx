Day7 做的事情看起来很简单: 把蛇头从“像素坐标移动”改成“网格坐标移动”。

但真正写下去以后我才发现，这不是一次普通的代码改动，而是一次很典型的结构重构。因为当你从像素世界切到网格世界，改变的不只是数值类型，而是整个游戏的表达方式。

## 今天到底改了什么

这一天的目标很明确:

- `playerX / playerY` 不再直接代表蛇头位置
- 改成 `headCol / headRow`，也就是第几列、第几行
- 屏幕上真正显示的位置，再由格子坐标换算成像素坐标
- 输入继续只负责方向，真正的位置更新交给 `Tick`

一句话概括就是:

> 从“像素在动”，变成“格子在动”。

## 先把问题说清楚

### 现象

前面的版本里，蛇头的位置还是用像素来表示的:

```cpp
playerX / playerY = 屏幕像素位置
```

这样当然能动，但它有一个很大的问题: 系统思考的是“点在哪个像素”，而不是“物体在哪个格子”。

对于一款想做成贪吃蛇的游戏来说，这种模型不够稳。因为贪吃蛇天然就是格子游戏:

- 每一步走到哪个格子
- 有没有撞墙
- 有没有和自己身体重叠
- 食物生成在哪个格子

这些问题，网格模型都更好处理。

### 原因分析

像素坐标的状态空间太大了。

屏幕上每一个像素都可能是一个不同状态，数值很多，看起来自由，但一旦要做规则判断，就会变复杂。你不仅要考虑位置，还要考虑像素边界、对齐、尺寸、渲染误差，后面再加碰撞，逻辑会越来越散。

而网格世界就不一样了。Day7 里我把它压到了一个很小、很稳定的空间:

- 16 列
- 16 行
- 每格 10 像素
- 游戏区 160x160

这意味着系统状态一下子就被收敛住了。

### 修复方式

我把逻辑世界和显示世界分开了。

逻辑世界只关心:

- 蛇头在第几列 `col`
- 蛇头在第几行 `row`

显示世界只负责把格子坐标换算成像素坐标:

```cpp
pixelX = GRID_ORIGIN_X + col * CELL_SIZE;
pixelY = GRID_ORIGIN_Y + row * CELL_SIZE;
```

这一步建立起来之后，后面的系统就会顺很多。

## 网格为什么选 16x16

这不是随便拍脑袋定的。

屏幕是 `170 x 320`，如果直接拿整块屏幕去做贪吃蛇网格，会有几个不舒服的地方:

- `170` 不是很多常见格子大小的整数倍
- 游戏区和 UI 区会挤在一起
- 后面还要留标题、分数、状态提示的位置

所以我先切出一个正方形游戏区:

- `160 x 160`
- 每格 `10 px`
- `16 x 16`
- 左右各留 `5 px` 边距

```cpp
const int CELL_SIZE = 10;
const int GRID_COLS = 16;
const int GRID_ROWS = 16;
const int GRID_ORIGIN_X = 5;
const int GRID_ORIGIN_Y = 40;
```

这种设计很朴素，但它带来的好处是很实在的: 游戏区从一开始就被约束住了，后面无论是移动、碰撞还是食物生成，都能围绕这个规则展开。

## 位置变量也要换一套语言

### 旧模型

旧版本里，我的蛇头大概是这样记的:

```cpp
int playerX = ...;
int playerY = ...;
```

这套写法的问题不是“不能用”，而是它太偏向渲染层了。

### 新模型

Day7 里我把它改成了逻辑坐标:

```cpp
int headCol = GRID_COLS / 2;
int headRow = GRID_ROWS / 2;
int dirX = 1;
int dirY = 0;
```

这时蛇头不再是“屏幕上的一个像素点”，而是“格子里的一个实体”。

这种改变很重要，因为从这以后，系统真正关心的是:

- 当前在哪个格子
- 下一步去哪个格子
- 有没有越界

而不是“画到哪一个像素更好看”。

## 把格子转成像素，交给单独函数

为了避免以后每个地方都手写一遍坐标换算，我把格子转像素抽成了函数。

```cpp
int cellToPixelX(int col) {
  return GRID_ORIGIN_X + col * CELL_SIZE;
}

int cellToPixelY(int row) {
  return GRID_ORIGIN_Y + row * CELL_SIZE;
}
```

这一步看起来很小，但它的意义是把“规则”从调用处拿走。
以后上层代码只关心 `(col, row)`，不用再管屏幕换算细节。

## Tick 里只改格子，不再改像素

以前的位置更新是这样的:

```cpp
playerX += dirX;
playerY += dirY;
```

Day7 里我把它改成了:

```cpp
headCol += dirX;
headRow += dirY;
```

这表示真正移动的单位已经从像素变成了格子。

为了先确保这一步测试稳定，我还加了一个临时边界保护，避免测试阶段直接跑出游戏区:

```cpp
headCol += dirX;
headRow += dirY;

if (headCol < 0) headCol = 0;
if (headCol >= GRID_COLS) headCol = GRID_COLS - 1;
if (headRow < 0) headRow = 0;
if (headRow >= GRID_ROWS) headRow = GRID_ROWS - 1;
```

这里很值得注意: 这不是最终版的“撞墙判死”，而只是一个临时保护。真正的越界判定后面还能继续单独做，但第一步先别让系统跑飞。

## 渲染也要跟着换思路

### 从圆点到方块

旧版本里，蛇头还是按像素画一个红点:

```cpp
tft.fillCircle(playerX, playerY, 5, TFT_RED);
```

网格化之后，这种画法就不合适了。因为它会让逻辑世界和显示世界再次混在一起。

所以我把它改成按格子画方块:

```cpp
int headX = cellToPixelX(headCol);
int headY = cellToPixelY(headRow);
tft.fillRect(headX + 1, headY + 1, CELL_SIZE - 2, CELL_SIZE - 2, TFT_RED);
```

这里故意留出一点边距，让方块不要糊成一片。这样看起来更像一个有格子的游戏区。

### 统一画格子的接口

接着我又把画格子的逻辑封装成了统一函数:

```cpp
void drawCell(int col, int row, uint16_t color) {
  int x = cellToPixelX(col);
  int y = cellToPixelY(row);
  tft.fillRect(x + 1, y + 1, CELL_SIZE - 2, CELL_SIZE - 2, color);
}
```

有了这个函数以后，蛇头、蛇身、食物都能统一走同一套画法。

这一步本质上是在告诉上层逻辑:

**不要直接操作像素细节，只要告诉我你要画哪个格子。**

### 把网格线也画出来

为了让“我现在真的是在网格系统里”这件事更直观，我还加了边框和网格线:

```cpp
tft.drawRect(
  GRID_ORIGIN_X - 1,
  GRID_ORIGIN_Y - 1,
  GRID_COLS * CELL_SIZE + 2,
  GRID_ROWS * CELL_SIZE + 2,
  TFT_WHITE
);

for (int c = 1; c < GRID_COLS; c++) {
  int x = GRID_ORIGIN_X + c * CELL_SIZE;
  tft.drawLine(x, GRID_ORIGIN_Y, x, GRID_ORIGIN_Y + GRID_ROWS * CELL_SIZE, TFT_DARKGREY);
}

for (int r = 1; r < GRID_ROWS; r++) {
  int y = GRID_ORIGIN_Y + r * CELL_SIZE;
  tft.drawLine(GRID_ORIGIN_X, y, GRID_ORIGIN_X + GRID_COLS * CELL_SIZE, y, TFT_DARKGREY);
}
```

这样一来，屏幕上的位置关系一下子就清楚了。

## 这次重构真正值钱的地方

Day7 最重要的收获，不是“画面更像贪吃蛇了”，而是系统的状态空间被压缩了。

以前，系统要处理的是像素级变化;
现在，系统处理的是格子级变化。

这意味着后面很多事情都会更容易:

- 判定是否越界
- 生成食物
- 判断蛇头是否撞到身体
- 让蛇身按格子增长

也就是说，这不是单纯的渲染重构，而是把游戏逻辑改写成了更稳定的表达方式。

## 从安全视角看这件事

这一步其实也很像输入降权的延伸版。

前几天我已经在做:

- 输入只改方向
- 方向不直接改结果
- Tick 统一结算移动

Day7 继续往前走了一步:

- 结果也不再直接落到像素上
- 而是落到有限网格里

这带来的安全收益很直接:

- 状态更少，边界更清楚
- 合法性检查更容易写
- 越界和冲突更容易发现

从开发者的角度看，这是重构;
从系统设计的角度看，这是把一个开放的像素空间收束成了一个可验证的逻辑空间。

## 今天的结论

Day7 不是“让蛇换了一种移动方式”，而是给整个项目补了一层真正适合贪吃蛇的世界模型。

它把之前那些零散的东西串起来了:

- 输入只负责方向
- Tick 负责推进
- 网格负责表达位置
- 渲染负责把格子画出来

这一步之后，我会更有底气去做后面的内容:

- 碰撞检测
- 蛇身数组
- 食物生成
- 撞墙处理

因为底层坐标系统已经稳了。

这就是 Day7 最让我踏实的地方: 它没有追求“更炫”，而是先把“更对”这件事做对了。
