Day5 的关键词只有一个: **权限控制**。

前面我们已经把 `LEFT / RIGHT` 接进来了，但问题也随之变得更真实了: 这些方向键不是任何页面都该响应的。菜单页不该用它们，图库页也不该用它们，只有 `STATE_GAME` 才应该把它们当成真正的游戏输入。

这就是今天要解决的事。

## 为什么输入权限必须绑定上下文

最开始我写的是很直接的处理方式: `handleLeft()`、`handleRight()` 收到输入后就直接去改逻辑。

但当系统开始长出页面后，你就会发现，输入不该是“全局随手可用”的。

<img
  src="/static/images/GameCC/input-permission-issues-table.png"
  alt="输入权限问题示意表，说明不是所有页面都应该响应同一套按键"
  width="700"
/>

这张表的意思很简单:

- 不连续移动，不代表系统必须停住
- 想做蛇这种玩法，移动必须交给统一节拍
- 输入过强，用户就会直接控制世界状态

所以问题不是“LEFT/RIGHT 能不能接”，而是“它们应该在哪个上下文里接”。

## 上下文隔离不是概念，是代码约束

我把 `handleLeft()` 和 `handleRight()` 都收进了 `switch (currentState)`，只允许它们在游戏态里真正生效。

```cpp
void handleLeft() {
  switch (currentState) {
    case STATE_GAME:
      // 游戏中才处理左移或转向
      break;
    default:
      break;
  }
}
```

这个改动看似小，但它的意义非常大:

**输入的合法性，不再由“有没有按键”决定，而是由“当前状态允不允许”决定。**

<img
  src="/static/images/GameCC/input-control-levels-table.png"

  width="700"
/>

从现在开始，输入不再是直接触发行为，而是先被状态机接住，再决定该不该执行。

## 先做一个假的游戏行为，把链路跑通

为了验证输入链路，我先没有把它接成完整游戏，而是做了一个很小的测试点: 在屏幕上画一个红点。

```cpp
int playerX = 80;
int playerY = 160;

void drawGamePage() {
  tft.fillCircle(playerX, playerY, 4, TFT_RED);
}
```

然后在 `STATE_GAME` 里，`LEFT` 和 `RIGHT` 直接控制这个点的横向移动。

这时候我想看的不是游戏好不好玩，而是三件事:

- 按键是不是只在游戏态生效
- 变量是不是能被稳定更新
- 重绘是不是跟着状态走

## 游戏主循环把时间也变成了输入

Day5 里最值得注意的变化之一，是 `Game Tick` 的引入。

这说明系统里除了按钮输入之外，还多了一种新的驱动力: 时间。

```cpp
if (currentState == STATE_GAME) {
  unsigned long now = millis();
  if (now - lastGameTick >= GAME_TICK_MS) {
    lastGameTick = now;
    playerX += 2;
    needsRedraw = true;
  }
}
```

这件事很关键，因为它告诉你:

**游戏不是“按一下才动”，而是“时间本身就在推动系统更新”。**

从安全角度看，这种时间驱动逻辑也很值得重视。它不是外部按钮，却会改变状态，所以它同样是一种输入源。只不过这个输入源是隐式的。

## 今天最重要的收获

Day5 之后，整个系统的边界感明显更强了:

- 输入不再全局有效
- 状态开始决定权限
- 游戏逻辑开始由 tick 驱动
- UI 刷新开始和状态变化分离

这不是简单的“多了一个功能”，而是输入模型开始成熟了。

对我来说，这一章最有价值的地方在于: 我第一次明显感受到，**状态机不只是页面切换工具，它也是输入权限管理工具。**

## 安全启发

如果把这章翻译成安全语言，大概就是这几句话:

- 不是所有输入都该在所有上下文里生效
- 系统状态应该先判断合法性，再决定是否执行
- 时间也是一种输入，不能当成“默认不会出事”的背景噪音

这其实已经很接近一个真正系统的边界设计方式了。

当一个按钮、一个 tick、一个页面状态都能影响结果时，你就必须开始认真考虑“最小作用域”。

而这恰好也是 Day5 这一步的意义。
