## 一、为什么“权限”是 Linux 安全模型的骨架？

在 Linux 世界里，几乎所有安全问题最终都会归结为一个问题：

> **“谁，被允许，对什么，做什么？”**

无论是文件读取、端口监听、进程调试，还是内核接口访问，背后都绕不开**权限判定**。

Linux 并不是一开始就复杂的。  
恰恰相反，它的权限系统是**从极简一路演化到今天的“多层防线”**。

---

## 二、DAC：Linux 最原始、也最熟悉的权限模型

### 2.1 什么是 DAC（Discretionary Access Control）？

DAC，中文叫**自主访问控制**，它的核心思想只有一句话：

> **资源的拥有者，决定谁能访问它。**

这就是你最熟悉的那套：

- UID / GID
- rwx 权限位
- `chmod` / `chown`

---

### 2.2 经典 DAC 权限判定流程

当进程访问一个文件时，内核会做这样的判断：

1. 进程的 UID 是不是文件 owner？
2. 否则，GID 是否匹配？
3. 否则，使用 others 权限
4. 若仍不满足 → 拒绝

这套模型**简单、直观、效率极高**，但它有一个致命问题。

---

### 2.3 DAC 的根本缺陷：root 是“上帝”

在 DAC 世界里：

> **root（UID 0）可以绕过一切。**

这意味着：

- 一旦程序拿到 root
- 所有文件、进程、设备
- 全部失守

这在早期 Unix 时代是可以接受的，但在现代系统中，这是一个**灾难级设计**。

---

## 三、Capabilities：把“上帝权限”拆碎

### 3.1 为什么需要 Capabilities？

Linux 引入 Capabilities 的动机非常直接：

> **不是所有程序都需要“完整的 root”。**

例如：

- 绑定 1024 以下端口 → 只需要 `CAP_NET_BIND_SERVICE`
- 修改时间 → 只需要 `CAP_SYS_TIME`
- 抓包 → 只需要 `CAP_NET_RAW`

于是 Linux 做了一件非常重要的事：

> **把 root 的能力拆成几十个独立的权限位。**

---

### 3.2 Capabilities 是“对谁”的？

Capabilities **不是给用户的**，而是给：

- **进程**
- **可执行文件**

它回答的是：

> “这个进程，额外被允许做哪些越权操作？”

---

### 3.3 一个经典例子

```bash
setcap cap_net_bind_service=+ep /usr/bin/myserver
```

效果是：

- 程序不是 root
- 但可以监听 80 端口
- 其他 root 权限一概没有

这直接降低了攻击成功后的破坏半径。

### 3.4 Capabilities 的三套集合（很关键）

Linux 内核内部，把 Capabilities 分成三组：

| 集合        | 含义                 |
| ----------- | -------------------- |
| Permitted   | 进程“可能拥有”的能力 |
| Effective   | 当前真正生效的能力   |
| Inheritable | 可传给子进程的能力   |

这套设计，使权限控制变得可组合、可收缩、可继承。

---

## 四、MAC：当“拥有者”也不再可信

### 4.1 DAC 的哲学前提

DAC 隐含一个前提：

> “用户是可信的。”

但在现实世界中：

- 应用可能被劫持
- 服务可能被 RCE
- root 也可能被利用

于是 Linux 引入了完全不同哲学的模型。

### 4.2 什么是 MAC（Mandatory Access Control）？

MAC，强制访问控制，核心思想是：

> 访问规则由系统统一制定，任何用户（包括 root）都不能绕过。

这是一种：

- 上帝视角
- 全局策略
- 不可协商的安全边界

### 4.3 SELinux / AppArmor 在干什么？

它们做的事情本质一样：

> 给进程和资源打“安全标签”，再定义谁能和谁交互。

例如：

- Web 进程只能读 /var/www
- 即使是 root shell，也不能随意读数据库文件
- 被攻破的服务，被锁死在“沙箱”里

### 4.4 一个关键认知（很多人误解）

> MAC 不是为了防“普通用户”，而是防“被攻破的 root 进程”。

这正是它存在的意义。

---

## 五、DAC / Capabilities / MAC 的分工关系

你可以把它们理解成三层防线：

```
第一层：DAC
  └─ 基础访问控制（谁能读写）

第二层：Capabilities
  └─ 精细化特权拆分（不用给 root）

第三层：MAC
  └─ 强制安全边界（root 也不能越界）
```

它们不是互斥的，而是叠加生效。

---

## 六、安全与漏洞视角：为什么理解权限模型很重要？

在安全研究中，很多问题本质是：

- 漏洞发生在哪一层？
- 能不能突破下一层？
- 权限是否被进一步收缩？

例如：

- RCE 但无 Capabilities → 影响有限
- root 但有 SELinux → 仍被限制
- 拿到 CAP_SYS_ADMIN → 几乎等价 root

理解权限模型，你才能真正评估漏洞价值。

---

## 七、总结：Linux 权限不是“一个开关”

Linux 的权限体系，已经从最初的：

> “你是不是 root？”

进化成了今天的：

> “你是谁？你被允许做什么？你被限制在哪？”

这是 Linux 能在服务器、云、IoT、安全设备中长期存活的根本原因之一。
