## 一、为什么 Syscall 是 Linux 的“唯一正门”？

在 Linux 中，用户程序几乎**什么都做不了**：

- 不能直接读磁盘
- 不能创建进程
- 不能操作网络
- 不能访问内核内存
- 不能执行特权指令

但现实中你每天都在：

```c
open();
read();
write();
fork();
execve();
```

这背后只有一个原因：

> **Linux 允许用户态通过 Syscall，请求内核代为执行特权操作。**

Syscall 的本质不是“跳转”，而是：

> **一次受 CPU 严格监管的特权级切换。**

---

## 二、从整体看：Syscall 在系统中的位置

先看一张逻辑图（非常重要）：

```
用户程序
  ↓
glibc 封装（open / read / write）
  ↓
syscall 指令（架构相关）
  ↓
内核统一入口
  ↓
sys_xxx() 内核函数
  ↓
返回用户态
```

👉 **用户态永远无法直接调用内核函数。**

---

## 三、CPU 视角：Syscall 到底“干了什么”？

不管是哪个架构，Syscall 都完成了这几件事：

1. CPU 当前在 **用户态**
2. 执行一条“系统调用指令”
3. **CPU 自动切换到内核态**
4. 切换到内核栈
5. 跳转到内核预设入口
6. 执行内核代码
7. 安全返回用户态

⚠️ 注意：  
**整个过程不是 Linux 决定的，而是 CPU 硬件强制完成的。**

---

## 四、x86 架构：syscall / sysenter

### 4.1 从 `int 0x80` 说起（历史）

早期 Linux 使用：

```asm
int 0x80
```

特点：

- 真·中断
- 保存大量上下文
- **慢，但通用**

---

### 4.2 现代主流：`syscall`

在 x86-64 中，Linux 默认使用：

```asm
syscall
```

执行后 CPU 会自动：

- CPL 3 → CPL 0
- RIP 跳转到 MSR 中指定的内核入口
- RSP 切换为内核栈
- 保存返回地址到 `RCX`
- 保存 RFLAGS 到 `R11`

📌 **这是一次“快速特权切换”，不是中断。**

---

## 五、ARM：SVC（Supervisor Call）

在 ARM 架构中，系统调用通过：

```asm
svc #0
```

完成。

其本质是：

> **主动触发一次同步异常**

流程是：

- EL0（用户态） → EL1（内核态）
- 跳转到异常向量表
- 进入 SVC handler

ARM 的设计哲学非常明确：

> **Syscall = 一种受控异常**

---

## 六、RISC-V：ecall（极简而优雅）

RISC-V 的系统调用只有一条指令：

```asm
ecall
```

含义：

- 从 U-mode 进入 S-mode
- 触发 Environment Call Exception
- 跳转到统一 trap handler

RISC-V 的理念是：

> **系统调用只是异常的一种。**

---

## 七、Syscall 参数是怎么传的？

这是二进制分析中非常关键的一点。

### 7.1 x86-64 Linux 约定

| 参数           | 寄存器 |
| -------------- | ------ |
| syscall number | RAX    |
| arg1           | RDI    |
| arg2           | RSI    |
| arg3           | RDX    |
| arg4           | R10    |
| arg5           | R8     |
| arg6           | R9     |

返回值：

- 成功：RAX ≥ 0
- 失败：RAX < 0（-errno）

---

### 7.2 为什么 glibc 很重要？

你在 C 里调用的是：

```c
read(fd, buf, len);
```

glibc 帮你做了：

- 设置寄存器
- 执行 syscall 指令
- 处理 errno

👉 **Syscall 很少被手写，但必须被理解。**

---

## 八、内核视角：Syscall 如何被分发？

进入内核后，流程大致是：

```
syscall entry
  ↓
保存寄存器
  ↓
检查 syscall number
  ↓
sys_call_table[nr]
  ↓
sys_read / sys_write / sys_open
```

这也是为什么：

- syscall number 越界会被拒绝
- 随意跳转是不可能的

---

## 九、安全视角：为什么 Syscall 是攻击焦点？

几乎所有用户态攻击，最终都要问：

- 能不能伪造 syscall 参数？
- 能不能劫持 syscall 返回？
- 能不能影响内核执行路径？

但同时：

> **Syscall 也是 Linux 最严密防护的入口之一。**

- 参数必须 copy_from_user
- 地址必须校验
- 特权严格分级

---

## 十、总结：Syscall 是一条被“精心设计的边界”

Syscall 解决的不是“怎么方便”，而是：

> **如何在不信任用户的前提下，让系统还能工作。**

它是：

- 用户态与内核态的分水岭
- 所有权限模型的入口
- 内核安全设计的核心支点
