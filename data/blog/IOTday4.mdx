# 揭秘 Linux 程序背后的“摩天大楼”：虚拟内存布局全解析

在深入 IOT 安全和二进制漏洞挖掘之前，你必须先搞清楚一个核心问题：**当你运行一个程序时，它在内存里到底长什么样？**
当你双击一个程序或者在终端输入 `./a.out` 时，Linux 系统并不仅仅是把代码丢进内存。它会为这个程序精心打造一座“虚拟大楼”。
今天，我们将通过一个极其形象的“大楼模型”，拆解 Linux 进程的内存布局，并利用 GDB 工具进行一场真实的“外科手术”。

---

## 第一部分：理论篇 —— 虚拟内存的“摩天大楼”模型

想象一下，Linux 内核是一个慷慨的地产商。每当你运行一个程序，它都会给这个程序分配一栋独立的、从 0 层到顶层（0x00000000 到 0xFFFFFFFF）的**摩天大楼**。这就是**虚拟内存（Virtual Memory）**。

虽然物理内存（RAM）可能像凌乱的仓库，但程序看到的永远是这栋整齐的大楼。

### 1. 代码段 (Text Segment) —— 【底层地基：只读】

- **是什么**：存放 CPU 直接执行的二进制指令。
- **特性**：**只读**。你不能在程序运行时修改自己的代码。如果你试图改写这里，系统会立刻抛出 `Segmentation Fault`（段错误）。
- **比喻**：大楼的承重墙和地基。你可以看图纸，但绝对不能乱拆。

### 2. 数据段 (Data Segment) —— 【仓库 A：已初始化变量】

- **是什么**：存放程序里那些**已经给了初始值**的全局变量和静态变量（static）。
- **比喻**：大楼装修时就运进来的家具，位置固定且已知。

### 3. BSS 段 (BSS Segment) —— 【仓库 B：未初始化变量】

- **是什么**：存放**没给初始值**的全局变量。系统在加载程序时会自动把这里清零。
- **为什么要分两类？**：为了省空间。Data 段的变量值需要存在硬盘的文件里，而 BSS 段只需要记个名字，运行后再清零，这样程序文件会更小。

### 4. 堆 (Heap) —— 【扩建区域：手动管理】

- **是什么**：程序员用 `malloc()` 手动申请的空间。
- **生长方向**：**从低往高长**。你申请得越多，楼层就盖得越高。
- **风险**：如果你 `malloc` 了但不 `free`，这块空间就永远被占用，导致“内存泄漏”。

### 5. 栈 (Stack) —— 【办公区域：自动管理】

- **是什么**：存放函数的参数、局部变量。
- **生长方向**：**从高往低长（倒着长！）**。这是为了让栈和堆在中间空旷的地带汇合，最大化利用空间。
- **特性**：先进后出（LIFO）。函数调用结束，这块内存自动回收。

## 第二部分：实战篇 —— 编写你的“解剖对象”

我们将编写一段 C 代码，故意在每个段里都放一个变量，然后观察它们的地址。

### 1. 编写代码

在你的 Ubuntu 终端输入 `nano memory_layout.c`：

```c
#include <stdio.h>
#include <stdlib.h>

// 1. 全局变量（已初始化） -> Data Segment
int global_init_var = 100;

// 2. 全局变量（未初始化） -> BSS Segment
int global_uninit_var;

void check_stack(int depth) {
    int local_val = depth;
    printf("栈深度 %d: 地址 %p\n", depth, &local_val);
    if (depth < 3) check_stack(depth + 1); // 递归观察栈向下生长
}

int main() {
    // 3. 局部变量 -> Stack
    int local_main = 1;

    // 4. 动态内存 -> Heap
    int *p_heap1 = (int *)malloc(100);
    int *p_heap2 = (int *)malloc(100);

    printf("=== 内存地址分布报告 ===\n");
    printf("[Text] main 函数地址:      %p\n", main);
    printf("[Data] 已初始化全局变量:   %p\n", &global_init_var);
    printf("[BSS ] 未初始化全局变量:   %p\n", &global_uninit_var);
    printf("[Heap] 第1次 malloc 地址:  %p\n", p_heap1);
    printf("[Heap] 第2次 malloc 地址:  %p\n", p_heap2); // 应该比上一个大
    printf("[Stack] main 局部变量:     %p\n", &local_main);

    check_stack(1); // 观察栈的地址变化

    printf("\n程序已暂停，请在另一个终端执行 GDB 或按回车结束...\n");
    getchar();

    free(p_heap1);
    free(p_heap2);
    return 0;
}
```

### 2. 编译

必须加上 `-g` 参数，否则 GDB 看不到源码调试信息。

```bash
gcc -g memory_layout.c -o memory_layout
```

## 第三部分：GDB 调试 —— 开启上帝视角

现在，我们要进入这栋大楼内部观察。

### 1. 启动调试

```bash
gdb ./memory_layout
```

### 2. 运行并观察映射

在 GDB 提示符下输入：

```bash
(gdb) break main       # 在入口打断点
(gdb) run              # 运行
(gdb) next             # 一直按 n 执行到 getchar 之前
```

此时，输入最核心的命令查看“大楼全景图”：

```bash
(gdb) info proc mappings
```

### 3. 地址规律大发现

通过观察打印出的地址，你会发现：

1.  **代码段地址很小**：通常以 `0x5555...` 或 `0x400...` 开头。
2.  **堆地址向上长**：`p_heap2` 的地址比 `p_heap1` 大。
3.  **栈地址非常大**：通常以 `0x7ffff...` 开头，且**越递归地址越小**（验证了向下生长）。

## 第四部分：进阶思考 —— 函数调用时发生了什么？

当你调用 `check_stack(1)` 时，系统会在“栈”区域压入一个**栈帧 (Stack Frame)**。

**栈帧里存了什么？**

1.  **返回地址**：函数做完后，CPU 应该回到 main 的哪一行？
2.  **函数参数**：传进来的 `depth` 是多少？
3.  **局部变量**：函数内部的 `local_val`。

**这就是著名的“栈溢出”原理：** 如果你写了一个死递归，栈会不断向下长，直到撞上堆或者超出预留的几 MB 空间，大楼就崩塌了。

## 总结：内存全景速查表

| 区域           | 存储内容               | 读写权限 | 生长方向                    |
| :------------- | :--------------------- | :------- | :-------------------------- |
| **Stack (栈)** | 局部变量、函数调用信息 | 读/写    | **向下 (高地址 -> 低地址)** |
| **Heap (堆)**  | `malloc` 申请的空间    | 读/写    | **向上 (低地址 -> 高地址)** |
| **BSS**        | 未初始化全局变量       | 读/写    | 固定                        |
| **Data**       | 已初始化全局变量       | 读/写    | 固定                        |
| **Text**       | 二进制代码指令         | **只读** | 固定                        |

掌握了这幅地图，你才真正开始了 Linux 安全的研究之路。下次当你看到 `0x7fffffffe450` 这样的地址时，你就知道：**哦，这哥们儿住在栈区！**
